# Screen evidence

Read for screen evidence or explanatory visual sequences, including code, diagrams, charts, and comparisons. This reference owns the viewing contract; HyperFrames owns rendering mechanics.

## Establish the contract

Use the entry point installed in the project. At production intake or after a skill update, record its resolved path and this reference's path and content hashes in the existing review record. Resolve missing references or version mismatches before certifying affected scenes; repository edits alone do not update installed copies.

Name what the viewer should understand or repeat. Map each spoken claim to a visible evidence state and narration cue. Choose presentation and timing from that job; a scene may combine these structures:

| Viewer job | Presentation and temporal structure |
| --- | --- |
| Follow an operation | Preserve source order: context → input → submission/execution → observed work → result → readable hold |
| Understand a mechanism | Make relationships primary; use bounded code or screen evidence to support the explanation |
| Read code or a field | Establish context → locate the excerpt or value → emphasize → hold → move attention |
| Interpret a chart | Establish scale and encoding before interpreting values; introduce data or emphasis at its cue, then hold the conclusion |
| Compare before and after | Use matched views and retain enough of both states to inspect the change |
| Follow branches or concurrency | Establish the condition or shared context; distinguish alternatives, simultaneous activity, and serial execution |
| Inspect topology or parallel categories | A complete or simultaneous view is valid; guide attention without implying causality |

Use full screen when the interface is the subject or controls need the space; use an inset when evidence supports a larger explanation. Give each crop or move an inspection purpose. Use stable holds when there is nothing new to inspect.

## Preserve evidence and operation context

For demonstrations, enter the source before the first action needed to understand the operation and retain its result. A declared result recap may show only the outcome. Retain source paths, recording in/out times, and trims, speed changes, or holds. Describe discrete still captures as step-by-step states. The existing `demo_contract` owns truth mode and code labels.

Distinguish generated implementation, existing framework APIs, real excerpts, and teaching illustrations at the relevant code surface.

For configuration, establish the normal entry path, selection, apply/save action, and persisted result. If the instance uses overrides or read-only controls, show the effective value and restriction rather than generalizing it to all users. For repeated startup commands, compare script expansion, checkout, working directory, state directory, and flags; distinguish behavior changes from instance selection.

## Plan states and readable holds

Carry the temporal structure and meaningful dependencies in the existing scene contract. In storyboard `Shot moments`, give each important state:

- A stable element/state ID and narration cue, or `silent`.
- Numeric intervals for entry and settling, emphasis or change, readable hold, and exit or handoff where timing matters.
- Dependencies: what remains visible, what changes, and what new information waits for a prior event.

Decorations need no separate inventory. A hidden target may reserve layout space before its content appears. Existing context can stay visible while emphasis moves.

A readable hold starts after the relevant content settles. Budget time to locate and read it at delivery size; typing and transitions consume separate time. “Appear with keywords” and an end-state proof do not specify a multi-step sequence.

If the required states exceed locked narration time, reuse relevant screen time, reduce taught actions, or propose a timing revision and record the tradeoff. Preserve user-recorded or explicitly locked audio unless its edit is authorized. Set hold durations by the reading task and verify them through playback.

## Animate causal diagrams

For authored diagrams introducing a new causal destination:

1. Finish revealing the source.
2. Draw the connector in its actual direction.
3. Reveal the destination, then hold the result.

Verify `source reveal end <= edge draw start` and `edge draw end <= new destination reveal start`. Inspect during the draw: the new destination's content must still be hidden. Order branch transfers by the explanation.

For a destination established in an earlier moment, retain it and apply arrival emphasis or a state update after transfer; identify its prior establishment. Captured interfaces retain their observed interaction order. Topology and parallel-category views use their declared inspection structure from the table above.

## Check the built timeline

Derive acceptance conditions from the viewer job and storyboard dependencies. Compare actual visibility, emphasis, and timing with those conditions, rather than validating timing copied from the implementation generator.

Sample boundary and intermediate states, including a pre-arrival state that exposes premature content. Direct and backward seeking must match forward evaluation at the same time. When adding or changing a timing check, verify it rejects a deliberately wrong order or premature result and accepts the intended order, including an applicable simultaneous or established-target case. A universal “both endpoints visible during drawing” test cannot validate new-target causal reveals.

## Complete viewing review

For each changed sequence, play the affected interval at delivery size and normal speed with audio; deliberately silent scenes receive silent playback review. Confirm cue alignment, readable controls and values, purposeful framing, declared state dependencies, and clear evidence labels. Layout checks and sampled stills establish different evidence from playback; a preview URL establishes access only.

In the existing review record, distinguish structural checks, timeline-state checks, and playback review. Record the project/source revision, actual reviewed interval, sampled states and holds, speed, audio status, and unresolved limitations. Keep unavailable playback or audio assessment pending rather than certifying delivery readiness. Timing, content, or audio changes invalidate the affected review; export the reviewed revision.
